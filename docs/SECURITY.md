## ۱. کارهای دستی — به ترتیب اولویت

### گام ۱ — قطع دسترسی مهاجم (فوری)

تغییر رمز به‌تنهایی کافی **نیست**: هرکس یک refresh token معتبر داشته باشد
همچنان داخل سامانه است.

1. **باطل‌کردن همه‌ی نشست‌ها** — `scripts/incident-response.sql` بخش ۱ را در
   Supabase → SQL Editor اجرا کنید.
2. **چرخاندن JWT Secret** — Dashboard → Project Settings → API → JWT Settings
   → «Generate new secret». این کار همه‌ی access tokenهای صادرشده را در همان
   لحظه بی‌اعتبار می‌کند.
3. بخش ۰ همان اسکریپت را اجرا کنید و خروجی ۰-۱ (فهرست ادمین‌ها) را با دقت
   ببینید: هر ردیف ناشناس، درِ پشتی مهاجم است.

### گام ۲ — تغییر رمز حساب ادمین **در خود Supabase**

> 🚨 مهم‌ترین نکته‌ی این سند. عوض‌کردن `ADMIN_PASSWORD` در env به‌تنهایی
> **کافی نیست**.

احراز هویت واقعی را GoTrue (سرویس auth خود Supabase) انجام می‌دهد و endpoint
آن برای اینترنت باز است. تا پیش از این تغییر، رمز حساب `amirkamali@kamali.local`
دقیقاً همان `ADMIN_PASSWORD` بود، بنابراین هرکس آن رمز را می‌دانست می‌توانست
بدون عبور از `verifyAdminLogin` مستقیماً وارد شود:

```js
supabase.auth.signInWithPassword({ email: "amirkamali@kamali.local", password: "<رمز قدیمی>" })
```

این مسیر همه‌ی قفل‌ها و سقف‌های نرخ را دور می‌زد.

**اقدام فوری:** Dashboard → Authentication → Users → `amirkamali@kamali.local`
→ Reset password → یک مقدار تصادفی بلند. همین لحظه رمز قدیمی بی‌اثر می‌شود.

پس از آن، کد جدید این مشکل را برای همیشه می‌بندد: رمز حساب Supabase دیگر
هرگز برابر `ADMIN_PASSWORD` نیست. در هر ورود موفق، سرور یک رمز تصادفی ۳۲
بایتی روی حساب می‌گذارد، سمت خودش وارد می‌شود و فقط «نشست» را به مرورگر
می‌دهد. یعنی حتی با دانستن `ADMIN_PASSWORD` هم ورود مستقیم به GoTrue ممکن
نیست و مهاجم مجبور است از `verifyAdminLogin` رد شود — جایی که قفل و سقف نرخ
اعمال می‌شود.

### گام ۳ — چرخاندن همه‌ی کلیدها

هر مقداری که تا امروز در `.env` مخزن بوده، **سوخته** است. مخزن عمومی است و
تاریخچه‌ی git پاک‌شدنی نیست (کلون‌ها و ایندکس‌ها باقی می‌مانند).

| متغیر | کجا | توضیح |
|---|---|---|
| `ADMIN_PASSWORD` | env هاست | مقدار جدید و تصادفی — نه شبیه قبلی |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → API | چرخانده شود |
| `MELIPAYAMAK_API_KEY` | پنل ملی‌پیامک | در `.env` مخزن لو رفته بود |
| `CRON_SECRET` | — | **حذف کنید**؛ هیچ کدی از آن استفاده نمی‌کند |

> ⚠️ `CRON_SECRET` در `.env` مخزن، بایت‌به‌بایت برابر همان رمزی بود که در
> کامیت `d76f716` به‌صورت hardcode در `src/routes/login.tsx` قرار داشت — یعنی
> رمز ادمین. آن فایل یک route است، پس این مقدار **در باندل مرورگر** به هر
> بازدیدکننده‌ی سایت سرو می‌شده است (۱۰ تا ۲۷ خرداد / 2026-06-10 تا 06-27).
> اگر رمز فعلی ادمین همان است، همین مسیر نفوذ بوده.

### گام ۴ — اعمال مهاجرت پایگاه داده

محتوای **هر دو** فایل زیر را در Supabase → SQL Editor اجرا کنید (ترتیب مهم
نیست؛ فایل دوم خودکفاست و اگر اولی جا مانده باشد همان را هم می‌سازد):

```
supabase/migrations/20260827120000_security_hardening.sql
supabase/migrations/20260827223000_security_hardening_v2.sql
```

بررسی سلامت:

```sql
SELECT public.check_rate_limit('smoke-test', 5, 60);   -- باید true برگرداند
```

اگر این تابع نباشد، کد جدید ثبت‌نام را قفل **نمی‌کند** (به شمارنده‌ی حافظه
برمی‌گردد) اما سقف سراسری بین چند سرور مشترک نخواهد بود. پس حتماً SQL را
اجرا کنید.

### گام ۵ — به‌روزرسانی `xlsx` (آسیب‌پذیری شناخته‌شده)

نسخه‌ی فعلی `xlsx@0.18.5` از npm است و دو CVE دارد که دقیقاً با **باز کردن یک
فایل اکسل مخرب** فعال می‌شوند — همان کاری که «ورود گروهی محصولات» انجام می‌دهد:

* CVE-2023-30533 — Prototype Pollution
* CVE-2024-22363 — ReDoS

بسته‌ی npm دیگر نگهداری نمی‌شود؛ نسخه‌ی اصلاح‌شده فقط از مخزن خود SheetJS
منتشر می‌شود:

```bash

npm i https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz
npm run build   # بررسی کنید ورود گروهی محصولات همچنان کار می‌کند
```

### گام ۶ — مخزن

```bash

git commit -m "chore: stop tracking .env"
```

`.gitignore` به‌روزرسانی شده و `.env.example` اضافه شده است. اگر مخزن عمومی
است، **خصوصی‌اش کنید** — تاریخچه‌ی کامل کلیدها در آن باقی می‌ماند.

### گام ۷ — بعد از پایدار شدن: سفت‌کردن CSP

منتقل کنید.

## ۲. کارهای انجام‌شده در کد

### اعتبارسنجی و محدودسازی نرخ

* زیرساخت مشترک: `src/lib/rate-limit.server.ts` + تابع اتمیک
  `check_rate_limit` در Postgres (بین همه‌ی نمونه‌های Worker مشترک است).
* **fail closed**: اگر بررسی سهمیه خطا بدهد، درخواست رد می‌شود.
* سقف‌ها: ثبت‌نام ۱۲/ساعت·IP و ۸۰/ساعت کل سامانه — نسخه‌ی آزمایشی ۲/روز·IP و
  ۲۰/ساعت کل — بازیابی رمز ۳/ساعت — آپلود رسید ۲۰/ساعت — کوتاه‌کننده‌ی لینک
  ۳۰/ساعت — تنظیم رمز و استعلام وضعیت ۱۰/ساعت.
* اگر تابع `check_rate_limit` هنوز در دیتابیس نباشد، ثبت‌نام با پیام «تعداد
  درخواست بیش از حد» قفل **نمی‌شود**؛ به شمارنده‌ی حافظه‌ی همان سرور برمی‌گردد.
  خطای واقعی اتصال دیتابیس همچنان fail-closed است.
* سطل مشترک `unknown` حذف شد: نبود IP دیگر همه‌ی کاربران را با هم قفل نمی‌کند.
* تله‌ی ربات (honeypot) و سقف ۳ درخواست در انتظار برای هر شماره موبایل در ۲۴ ساعت.
* Cloudflare Turnstile روی ثبت‌نام و بازیابی رمز: ویجت سمت کلاینت + تایید
  `siteverify` سمت سرور (`src/lib/turnstile.server.ts`). تا وقتی
  `TURNSTILE_SECRET_KEY` در Vercel نباشد، بررسی رد می‌شود تا سایت نخوابد.
  راهنمای کلیدها: `docs/RAHNAMA-TURNSTILE.md`.
* سقف طول روی همه‌ی رشته‌های ورودی عمومی؛ حذف کاراکترهای کنترلی.
* سیاست رمز: حداقل ۸ کاراکتر، ترکیب حرف و عدد (قبلاً ۶ کاراکتر بدون شرط).

### ورود ادمین

* قفل پس از ۵ تلاش ناموفق در ۱۵ دقیقه برای هر IP، و ۲۰ تلاش در کل سامانه
  (جلوی حمله‌ی توزیع‌شده).
* مقایسه‌ی زمان‌ثابت واقعی: طرفین SHA-256 می‌شوند، پس **طول رمز دیگر از
  روی زمان پاسخ لو نمی‌رود** (نسخه‌ی قبلی با مقایسه‌ی طول شروع می‌شد).
* یوزرنیم ادمین دیگر از طریق فرم ثبت‌نام قابل کشف نیست: پیام «این یوزرنیم
  رزرو شده است» با پیام عادی «تکراری» یکسان شد.
* یافتن حساب ادمین از روی `profiles` (O(1)) به‌جای اسکن صفحه‌ی اول ۲۰۰ کاربر.
* **جداسازی رمز GoTrue از ADMIN_PASSWORD** — مهم‌ترین تغییر این بخش. قبلاً
  کلاینت خودش `signInWithPassword` می‌زد، پس هرکس ADMIN_PASSWORD را داشت
  می‌توانست مستقیم وارد GoTrue شود و قفل/سقف نرخ را کامل دور بزند. حالا سرور
  اعتبارسنجی می‌کند، رمز حساب را به یک مقدار تصادفی تازه تغییر می‌دهد و فقط
  نشست را به مرورگر می‌دهد. (جزئیات در گام ۲)

### افشای اطلاعات

* ستون `signup_requests.temp_password` **حذف شد**. رمز کاربران دیگر هرگز
  به‌صورت متن ساده ذخیره نمی‌شود.
* لغو GRANTهای بی‌استفاده روی `signup_requests`، `profiles` و `app_settings`.

### XSS در چاپ فاکتور

مسیر: `print.ts` خروجی را در `iframe.srcdoc` (هم‌مبدأ، بدون sandbox) رندر
می‌کند و نشست Supabase در `localStorage` همان مبدأ است — یعنی تزریق اسکریپت
یعنی سرقت توکن.

* یک escaper مشترک و کامل: `src/lib/html-escape.ts` (شامل `"` و `'` که هر دو
  نسخه‌ی قبلی رها می‌کردند و در جایگاه صفت ناامن بودند).
* همه‌ی سازنده‌های HTML اصلاح شدند: فیش حرارتی فروش، فاکتور خرید A4 و
  حرارتی، صفحات QR منو و فروشگاه.
* `accent` قالب فاکتور که مستقیم داخل `<style>` درج می‌شد، حالا فقط هگز
  معتبر می‌پذیرد (`safeCssColor`).
* تست: `node scripts/test-html-escape.mjs`

### سوءاستفاده از سرویس‌های پولی

`transcribeAudio`، `parseVoiceInvoiceLLM` و `parseVoiceProductLLM` فقط توکن
معتبر می‌خواستند — یعنی یک حساب آزمایشی رایگان می‌توانست بی‌نهایت درخواست به
کلیدهای ANTHROPIC/OPENAI بزند. حالا **اشتراک فعال** + سهمیه‌ی ساعتی لازم است.

### آپلود رسید

* فقط پسوندهای تصویری (قبلاً `receipt.html` هم پذیرفته می‌شد).
* نوع محتوا سمت کلاینت به `image/*` تثبیت شد.
* `getReceiptSignedUrl` پیش از ساخت لینک، **بایت‌های ابتدایی فایل** را بررسی
  می‌کند؛ فایلی که تصویر نباشد نمایش داده نمی‌شود.
* اعتبارسنجی الگوی مسیر (جلوگیری از path traversal).

### سایر

* گزارش عملیات ادمین: جدول `admin_audit_log` (ورود موفق/ناموفق، تایید و رد
  درخواست، حذف کاربر، تغییر رمز، تمدید اشتراک). ادمین فقط می‌تواند بخواند.
* حذف حساب: هیچ ادمینی ادمین دیگر را حذف نمی‌کند؛ پیش از حذف، snapshot داده‌ها
  در `user_data_backups` ذخیره می‌شود. حذف فقط با تایپ یوزرنیم + رمز ادمین و
  حداکثر ۳ بار در ۳۰ دقیقه ممکن است — جلوی پاک‌کردن لحظه‌ای همه‌ی کاربران.
* تغییر رمز کاربر از پنل هم به رمز ادمین نیاز دارد (نشست دزدیده‌شده کافی نیست).
* تب ورود ادمین از صفحه‌ی `/login` عمومی برداشته شد؛ فقط مسیر `/admin`.
* نقش ادمین دیگر از کش `localStorage` خوانده نمی‌شود (آفلاین = غیرادمین).
* `openExternal` فقط اسکیم‌های مجاز را باز می‌کند (جلوی `javascript:`).
* سرآیندهای امنیتی روی همه‌ی پاسخ‌ها (`src/server.ts`).
* حذف endpoint نمونه‌ی بلااستفاده‌ی `getGreeting` (عمومی و بی‌سقف بود).
* `check_rate_limit`، `is_locked_out` و بقیه‌ی توابع SECURITY DEFINER با
  `SET search_path` تثبیت شدند.

## ۳. بازیابی داده‌های حذف‌شده

`user_data_backups.user_id` هیچ کلید خارجی ندارد، پس با حذف حساب‌ها
cascade **نشده** است. تا ۴۰ snapshot برای هر کاربر باقی مانده:

```sql
SELECT user_id, created_at,
       snapshot->'settings'->>'shopName' AS shop,
       jsonb_array_length(snapshot->'products') AS products,
       jsonb_array_length(snapshot->'invoices') AS invoices
  FROM public.user_data_backups
 ORDER BY user_id, created_at DESC;
```

`profiles` با حذف حساب پاک شده، پس نگاشت `user_id ↔ username` از بین رفته؛
برای تطبیق از `shopName` داخل snapshot و ردیف‌های باقی‌مانده‌ی
`signup_requests` (که username دارند) استفاده کنید.

## ۴. اطلاع‌رسانی به کاربران

تا پیش از این تغییرات، رمز انتخابی هر کاربرِ در انتظار تایید به‌صورت **متن
ساده** در `signup_requests.temp_password` ذخیره و در پنل ادمین نمایش داده
می‌شد. هرکس به پنل دسترسی داشته، آن‌ها را دیده است. کاربرانی که همان رمز را
جای دیگری هم استفاده می‌کنند باید مطلع شوند.
