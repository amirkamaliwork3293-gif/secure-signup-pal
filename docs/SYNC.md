# همگام‌سازی بین دستگاه‌ها — چه چیزی خراب بود، چه چیزی عوض شد، چه کاری لازم است

تاریخ: ۲۰۲۶-۱۱-۱۶ · شاخه: `claude/elegant-cerf-ek7ota`

## ۱) چرا «چیزی که روی سیستم ثبت می‌کنم روی گوشی نمی‌آید»

پنج علت جدا پیدا شد. هر کدام به‌تنهایی همین نشانه را می‌سازد.

| # | علت | نتیجه برای کاربر |
|---|---|---|
| ۱ | **اپ اندروید با یک تست اتصال ناموفق «آفلاین» می‌ماند.** اتصال فقط یک بار هنگام باز شدن برنامه با مهلت ۲٫۵ ثانیه بررسی می‌شد و دیگر تکرار نمی‌شد. | روی اینترنت کند، گوشی تا بسته شدن برنامه نه چیزی می‌گرفت و نه می‌فرستاد. |
| ۲ | **از دست رفتن بی‌صدای نشست.** اگر هنگام باز شدن برنامه تازه‌سازی توکن جواب نمی‌داد، برنامه با دادهٔ روی دستگاه باز می‌شد و همگام‌سازی تا بارگذاری مجدد خاموش می‌ماند؛ هیچ پیامی هم نشان داده نمی‌شد. | دستگاه «وارد شده» به نظر می‌رسید ولی جدا از بقیه کار می‌کرد. |
| ۳ | **حلقهٔ بی‌پایان بین دستگاه‌ها.** وقتی دو دستگاه تب فعالِ متفاوتی در فاکتورهای باز داشتند، یا یک ردیف را با فاصلهٔ کمتر از یک ثانیه ویرایش می‌کردند، هر کدام نسخهٔ خودش را نگه می‌داشت و بی‌وقفه دوباره آپلود می‌کرد. | دو دستگاه دو مقدار متفاوت نشان می‌دادند؛ مصرف شدید Disk IO و ترافیک. |
| ۴ | **جابه‌جایی کل داده با هر تغییر.** هر ذخیره کل ستون (مثلاً همهٔ فاکتورها) را می‌فرستاد، قبلش کل کالاها و فاکتورها را دانلود می‌کرد، و دستگاه دیگر کل ردیف را می‌گرفت. | برای فروشگاه پرکار چند مگابایت در هر ثبت؛ روی اینترنت ضعیف به مقصد نمی‌رسید. |
| ۵ | **تکیه بر سیگنال لحظه‌ای.** سیگنال با WebSocket مستقیم به `supabase.co` می‌آید که روی خیلی از شبکه‌ها وصل نمی‌شود؛ جایگزینش بررسی هر ۴۰ ثانیه بود و بعد از ۶ شکست تلاش برای اتصال قطع می‌شد. | تأخیر طولانی در رسیدن تغییرات. |

## ۲) چه چیزی عوض شد

**بدون نیاز به هیچ کاری روی سرور (با انتشار همین کد فعال می‌شود):**

- اپ اندروید با یک بار جواب ندادن آفلاین نمی‌شود و تا برگشتن اتصال، خودش دوباره بررسی می‌کند.
- نشستِ ازدست‌رفته خودکار برمی‌گردد؛ تا آن موقع نوار هشدار نشان داده می‌شود. اگر نشست واقعاً باطل شده باشد دکمهٔ «ورود دوباره» می‌آید (دادهٔ روی دستگاه، حتی ذخیره‌نشده، حفظ می‌شود).
- حلقه‌های بی‌پایان بسته شد: همهٔ دستگاه‌ها بین دو نسخهٔ یک ردیف یک انتخاب می‌کنند و «تب فعال» دیگر تغییر حساب نمی‌شود.
- قبل از هر ذخیره دیگر کل کالاها و فاکتورها دانلود نمی‌شود.
- بدون سیگنال لحظه‌ای، تا کاربر مشغول کار است هر ۸ ثانیه یک درخواست خیلی کوچک بررسی می‌کند چیزی عوض شده یا نه.

**با اجرای یک فایل SQL (بخش ۳) — همگام‌سازی «فقط تغییرات»:**

- هر دستگاه فقط ردیف‌هایی را که عوض کرده می‌فرستد و فقط ردیف‌های عوض‌شدهٔ دیگران را می‌گیرد.
- نمونهٔ اندازه‌گیری‌شده روی PostgreSQL محلی، حسابی با ۱۰٬۰۰۰ فاکتور: ثبت یک فاکتور ≈ ۷۰۰ بایت به‌جای ≈ ۵ مگابایت.
- باز کردن دوبارهٔ برنامه فقط تغییرات از آخرین بار را می‌گیرد؛ هر ۱۲ ساعت یک بار کل داده برای اطمینان تطبیق داده می‌شود.
- اگر این توابع روی سرور نباشند یا خطا بدهند، برنامه خودش به روش قبلی برمی‌گردد.

## ۳) کاری که باید انجام دهید — به همین ترتیب

1. **پشتیبان بگیرید:** Supabase → Database → Backups.
2. **SQL را اجرا کنید:** Supabase → SQL Editor، محتوای این فایل را کامل بچسبانید و Run بزنید:
   `supabase/migrations/20261115120000_sync_delta.sql`
   - فقط چیز اضافه می‌کند؛ هیچ جدول، ستون یا ردیفی حذف یا بازنویسی نمی‌شود.
   - اجرای دوباره‌اش بی‌ضرر است.
   - نسخه‌های قدیمی برنامه که هنوز روی گوشی‌ها باز هستند بدون تغییر کار می‌کنند.
3. **بررسی کنید که نصب شده:** این را در SQL Editor اجرا کنید؛ باید دو ردیف برگرداند.
   ```sql
   SELECT proname FROM pg_proc WHERE proname IN ('kamix_sync_push', 'kamix_sync_pull');
   ```
4. **کد را منتشر کنید:** این شاخه را در `main` ادغام کنید تا Vercel نسخهٔ جدید را بسازد.
   اپ اندروید همان سایت را بارگذاری می‌کند، پس ساخت APK جدید لازم نیست.
5. **آزمایش با دو دستگاه** (یک حساب روی گوشی و سیستم):
   - روی سیستم یک کالا اضافه کنید؛ بدون بارگذاری مجدد باید ظرف چند ثانیه روی گوشی بیاید.
   - روی گوشی یک فاکتور ثبت کنید؛ فاکتور و موجودی باید روی سیستم بیاید.
   - روی یکی کالایی را حذف کنید؛ باید از دیگری هم برود و برنگردد.

ترتیب ۲ و ۴ مهم نیست: کد جدید بدون SQL هم کار می‌کند (با روش قبلی) و SQL بدون کد جدید اثری روی کاربران ندارد.

**اگر مهاجرت‌های ۲۰۲۶-۱۰-۰۲ را قبلاً اجرا نکرده‌اید** (بخش ۴ از `DATA_SAFETY_REPORT.md`)، آن‌ها را هم اجرا کنید؛ مستقل از این فایل هستند و اجرای دوباره‌شان بی‌ضرر است.

## ۴) اگر مشکلی پیش آمد

- **SQL:** `supabase/rollbacks/20261115120000_sync_delta.rollback.sql` را اجرا کنید. فقط همان چیزهایی را که این مهاجرت اضافه کرده برمی‌دارد (شماره نسخه و شناسهٔ ردیف‌ها؛ هیچ دادهٔ کاربری در آن‌ها نیست). برنامه‌ها خودشان به روش قبلی برمی‌گردند.
- **کد:** ادغام را برگردانید. نسخهٔ قبلی برنامه با SQL جدید سازگار است.

## ۵) اختیاری

Supabase → Authentication → Sessions → «Refresh token reuse interval» را از ۱۰ به ۳۰ ثانیه برسانید. روی اینترنت ناپایدار احتمال باطل شدن نشست را کمتر می‌کند.

## ۶) آزمون‌ها

| آزمون | اجرا | چه چیزی را ثابت می‌کند |
|---|---|---|
| توابع SQL | `PGHOST=… PGPORT=… PGUSER=postgres scripts/sql-tests/run.sh` (فقط PostgreSQL آزمایشی) | ادغام ردیف‌به‌ردیف، دفتر مشتری، حذف‌ها، RLS، اجرای دوباره، rollback، زمان اجرا روی حساب سنگین |
| دو دستگاه | `npx tsx --tsconfig scripts/tsconfig.sync-test.json scripts/test-sync-two-devices.ts` | ۱۵ سناریو در ۴ حالت سرور (با و بدون مهاجرت جدید، با و بدون تریگر محافظ) + ۹ سناریوی «فقط تغییرات» |
| تصادفی سه دستگاه | `SEEDS=40 npx tsx --tsconfig scripts/tsconfig.sync-test.json scripts/test-sync-fuzz.ts` | بعد از صدها عملیات تصادفی، شبکهٔ کند و بستن/باز کردن برنامه: هیچ ردیفی گم نمی‌شود، هر سه دستگاه و سرور یکسان‌اند و دیگر آپلودی انجام نمی‌شود |
| اتصال اپ اندروید | `npx tsx --tsconfig scripts/tsconfig.sync-test.json scripts/test-online-reprobe.ts` | برنامه خودش از حالت آفلاین بیرون می‌آید |
| سرتاسری روی سرور واقعی محلی | `scripts/e2e/run-real-server.sh` (به PostgREST نیاز دارد) | **نوشته شده ولی هنوز اجرا نشده است** |

## ۷) چیزهایی که عوض نشد

- **موجودی کالا** هنوز یک عدد روی ردیف کالاست. اگر دو دستگاه همان کالا را در یک لحظه بفروشند، یکی از دو کسر ممکن است گم شود (هر دو دستگاه یک عدد یکسان نشان می‌دهند، ولی عدد یک واحد بیشتر است). راه درست، دفتر گردش موجودی است که تغییر بزرگی در مدل داده است.
- **نوشتن آفلاین در اپ اندروید** همچنان بسته است (تصمیم قبلی محصول).
